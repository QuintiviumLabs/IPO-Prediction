IPO Model Runbook

Everything needed to go from a bare work laptop to a trained model on your own IPO dataset: environment, data assembly, validation, the runs, and how to read what comes out.

The pipeline is plain Python with no database and no services. You assemble four CSV files in one folder; every script reads that folder. That is also why moving machines is easy — the repo plus that folder is the project.

01 Install the environment

One time per machine, about 15 minutes including downloads.

Install Python 3.11 — tick “Add python.exe to PATH” in the installer — and Git for Windows. Then open PowerShell and run, from wherever you keep projects:

git clone https://github.com/QuintiviumLabs/Test.git ipo-model
cd ipo-model
py -3.11 -m venv .venv
.venv\Scripts\activate
python -m pip install --upgrade pip
pip install -r requirements.txt
pip install -e .

If activation is blocked — corporate laptops often disable scripts. Run this once, then retry the activate line:

Set-ExecutionPolicy -Scope CurrentUser RemoteSigned

Prove it works before touching real data

This generates a fake dataset and runs the baseline on it. If you see per-fold metrics, the whole stack is functional.

python scripts\make_synthetic_data.py --out demo_data --n-ipos 400
python scripts\check_data.py --data demo_data
python scripts\run_baseline.py --data demo_data

Every later session starts with just: cd ipo-model then .venv\Scripts\activate (your prompt gains a (.venv) prefix).

02 Connect your dataset

Create a folder named data in the repo and build these files in it. Column names must match exactly; dates are YYYY-MM-DD.

ipos.csv — your company CSV, renamed

ColumnWhat goes in it
ipo_idAny unique string per deal — ticker is fine
first_trade_dateFirst day of trading
offer_priceIPO offer price
marketMarket label, e.g. HK, US. Must match market.csv
deal_sizeProceeds raised — any consistent unit
is_tmt, is_healthcare0 or 1
bk_*One 0/1 column per bookrunner — bk_goldman, bk_ms, … Multiple 1s per deal is expected
is_target (optional)1 = model this deal, 0 = momentum-universe only
bbg_ticker (optional)Bloomberg ticker if it differs from ipo_id

About is_target. The F1/F2 momentum factors read “the 10 most recent IPOs in this market” out of this same file. If your 1,570 deals are a filtered subset of each market, those factors misread the market.

Fix: add the market’s other IPOs with is_target=0. They feed the factors but are never trained or tested on, need only ~6 trading days of prices, and can leave deal_size, sector and bookrunner columns blank.

prices.csv, market.csv — Bloomberg

prices.csv is long format ipo_id,date,close, roughly the first 30 trading days per deal. market.csv is date,market,close — one benchmark index per market, since the model predicts outperformance against each deal’s own benchmark.

With the Terminal running and logged in, script both at once:

pip install --index-url https://blpapi.bloomberg.com/repository/releases/python/simple/ blpapi
pip install xbbg

# smoke test on 5 deals first — inspect the output
python scripts\pull_bloomberg.py --data data --benchmarks "HK=HSI Index,US=SPX Index" --limit 5

# then the full pull (resumable; bad tickers are logged, not fatal)
python scripts\pull_bloomberg.py --data data --benchmarks "HK=HSI Index,US=SPX Index"

Or by hand in Excel, one deal per block, stacked into a long sheet:

=BDH("0700 HK Equity","PX_LAST",first_trade_date,first_trade_date+45,"Days=T","Fill=P")
=BDH("HSI Index","PX_LAST",start,end)

Survivorship. Build the IPO list from a historical screen (IPO <GO>), which includes companies that later delisted. A list from current index membership drops exactly the failures — inflating every momentum factor precisely when the market was worst. Capture the FIGI/BBGID at export; plain tickers of delisted names often no longer resolve.

gpr.csv — geopolitical risk, from the web

python scripts\fetch_gpr.py --out data\gpr.csv

If your firewall blocks it, download the daily file from matteoiacoviello.com/gpr.htm in a browser, then convert:

python scripts\prepare_gpr.py --in Downloads\data_gpr_daily_recent.xls --out data\gpr.csv

deals.csv — optional, this is where your follow-on data goes

date,market,sector,proceeds covering IPOs and follow-ons and convertibles, sector one of tmt / healthcare / other. It upgrades the F3/F4 supply factors to the all-deal-types version. Without it they fall back to IPOs only.

03 Validate before running anything

This is a check-fix loop, not a one-shot. Every problem prints as a specific instruction rather than a stack trace mid-run.

python scripts\check_data.py --data data

It flags missing columns, unparseable dates, duplicate IDs, benchmark series that start too late for a market’s first IPO, deals with too few closes, and the target/universe split. Fix everything marked ERROR; read the warning lines and decide.

04 Run the models

Always pass --config configs\small.yaml — it carries the settings tuned for a ~1,500-row sample (smaller quantile band, 4 folds, 7 seeds).

# 1. the bar to clear — gradient-boosted trees, both engines, under a minute
python scripts\run_baseline.py --data data --config configs\small.yaml --engine both

# 2. the neural model on its own, single seed — fast iteration
python scripts\run_full.py --data data --config configs\small.yaml --seeds 0

# 3. the main run: every rung, full seed ensemble -> results\ablations.md
python scripts\run_ablations.py --data data --config configs\small.yaml

# 4. why it behaved that way
python scripts\diagnose.py --data data --config configs\small.yaml
CommandRough timeProduces
run_baseline.py< 1 minPrinted metrics per fold
run_full.py --seeds 0~1 minPrinted metrics per fold
run_ablations.py20–40 minresults\ablations.md and .csv
diagnose.py5–15 minresults\diagnostics\*.csv

Laptop CPU, ~1,500 deals. No GPU needed — the model is about 1,700 parameters.

05 Read the results

Open results\ablations.md. Each row is a model variant, each number is mean ± standard deviation across the time-ordered folds.

MetricWhat it meansWhat is good
rank_icCorrelation between predicted and realised ranking of deals — the headline number0.05–0.15 is a real result on live data
decile_spreadTop-decile minus bottom-decile realised outperformancePositive and stable across folds
coverageHow often the truth landed inside the predicted bandClose to nominal_coverage
maeAverage size of the missLower, but noisy on fat tails

The one comparison that matters. The deep rungs must beat rung 0_lgbm. If they do not, the honest finding is that engineered features and gradient boosting are sufficient — which is a perfectly publishable result, and the ablation ladder is what lets you say it with evidence.

Read the standard deviation too. A mean rank IC of 0.12 ± 0.02 is a signal; 0.12 ± 0.20 is one lucky fold.

Then results\diagnostics\: permutation_importance.csv ranks features by how much rank IC drops when each is shuffled — a negative value means the feature is actively hurting. slice_metrics.csv breaks performance down by market, sector and risk regime, turning “it underperforms” into “it underperforms in low-issuance windows”.

06 When something breaks

SymptomCause and fix
python is not recognised PATH was not set at install. Use py -3.11 instead, or reinstall Python with the PATH box ticked
Cannot run activate — scripts disabled Set-ExecutionPolicy -Scope CurrentUser RemoteSigned, then retry
ModuleNotFoundError: ipo_model The venv is not active, or pip install -e . was skipped
ImportError: blpapi Install it from Bloomberg’s own index — the plain PyPI name will not work
Bloomberg returns nothing for a ticker Usually a delisted name. Use the FIGI/BBGID. Check bloomberg_failures.csv for the full list
fetch_gpr.py fails Firewall or a moved link. Download in a browser and use prepare_gpr.py
check_data: benchmark starts on/after first IPO Re-pull that index with an earlier start date — it needs history before the first deal
rank IC near zero everywhere Expected on real data at first. Check diagnose.py output before changing the model

07 Moving to another machine

Two things carry the project: the git repo and your data\ folder. On the new machine, repeat step 01, copy data\ across, and run check_data.py.

Never copy .venv\. It hard-codes absolute paths and will fail in confusing ways. Always recreate it — that is what step 01 is for.

Commit your work before switching machines. data\ and results\ are git-ignored on purpose, so keep them backed up separately if they matter.
